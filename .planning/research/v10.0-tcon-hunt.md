# v10.0 TCON Hunt: Software-Only Panel Controller Identification & GOP-Init Mapping

**Question:** How do we identify the D330's DSI panel TCON controller and map what the GOP
programs, using ONLY the running kernel and the existing `i915_dsi_regs` dump node (no hardware)?

**Headline result:** the local decode done in this session killed the "block-55 mystery" —
**VBT block 55 is DSC compression parameters (old format), never parsed by the kernel, and
not the panel-init table.** Meanwhile the VBT's own **panel PnP ID names the glass: AUO**.
The concrete software-only instrument that closes the remaining gap is a **DCS ID read
(0x04 / 0xDA 0xDB 0xDC) extension of the existing dump node** — feasible because the host
transfer path implements RX and BTA is enabled in the VBT config.

---

## 1. VBT block-55 structure — DECODED (Q1)

### 1.1 Public truth of the block ID (kernel source, HIGH confidence)

From `drivers/gpu/drm/i915/display/intel_vbt_defs.h` (mainline):

```c
BDB_RGB_PALETTE			= 54, /* 180+ */
BDB_COMPRESSION_PARAMETERS_OLD	= 55, /* 198-212 */
BDB_COMPRESSION_PARAMETERS	= 56, /* 213+ */
```

- **Block 55 = `BDB_COMPRESSION_PARAMETERS_OLD`, valid only for BDB versions 198–212.**
  The D330 runtime VBT is BDB **212** — exactly the last version using this old ID.
  (The `struct bdb_rgb_palette` doc comment above it is a stale leftover; the enum governs.)
- `intel_bios.c` `bdb_blocks[]` (the kernel's only parse table) has an entry for
  **`BDB_COMPRESSION_PARAMETERS` (56)** but **NO entry for 55** — and
  `parse_compression_parameters()` calls `bdb_find_section(display,
  BDB_COMPRESSION_PARAMETERS)` exclusively. **The kernel never parses block 55 on any
  VBT version.** Same story in igt: the D330 decode printed `BDB block 55 (258 bytes,
  min 0 bytes) - Unknown` (`docs/dumps/re_kit/runtime_vbt_decode.txt:945`,
  `b53_full.txt:43`).
- Block-56 struct (kernel, HIGH): `struct bdb_compression_parameters { u16 entry_size;
  struct dsc_compression_parameters_entry data[16]; }` where each entry starts with
  `version_major:4 | version_minor:4` (DSC version, e.g. `0x11` = DSC 1.1).

### 1.2 The D330's block 55, decoded locally this session

Parsed `docs/dumps/re_kit/runtime_vbt.bin` (5755 B, "$VBT GEMINILAKE", BDB 212,
header 22 B, blocks from offset 70). Block layout per `intel_bios.c::_get_blocksize()`:
normal blocks = `id u8 + size u16 LE`; **block 53 v3 is the exception** = 8-byte header
(`id u8, size u16 [unused], version u8, size u32 LE`). This resolves the kit-vs-tool
size discrepancy: at file offset 5527 the bytes `35 00 00 | 03 | dc 00 00 00` are block 53
(version 3) with **220 B** payload + 5-byte v3 header = igt's "225 bytes" (225 = 220+5,
per `init_bdb_block()`'s `block_size += 5`).

Block 55 found at file offset **5266** (`37 02 01` = id 55, size 258), payload:

```
u16 0x0080 (128) + 2 × 128-byte entries (LFP1, LFP2 — matches block 53's panel mask)
entry[0] @rel2 : 11 00 00 80 00 20 00 ... 00 0c 00 00 00 00 00 18 00 00
                 03 0c 00 00 00 0b 0b 00 0e 1c 2a 38 46 54 62 69 70 77 79 7b 7d 7e
                 80 08 80 00 a1 00 c1 f8 e3 f0 e3 e8 e3 e0 03 e1 23 e1 43 d9 65 d9
                 85 d1 a5 d1 a7 d1 ed d1 (then zeros to 128 B)
entry[1] @rel130: 11 00 00 80 00 30 00 ... (identical except:)
   r5: 0x20→0x30   r17,r18: 80 00→01 55   r27: 0x0c→0x0f   r33: 0x18→0x08
   r58: 0x80→0x40
```

Structural reads (MEDIUM — no public field map for the old 128-B entry format):
- first byte `0x11` per entry = **DSC version 1.1** (major 1, minor 1) — same nibble
  split as the block-56 entry;
- a 17-byte monotonic ramp `0x0b 0x0b 0x0e 0x1c 0x2a 0x38 0x46 0x54 0x62 0x69 0x70 0x77
  0x79 0x7b 0x7d 0x7e` then `0x80` (128 = the `u16 0x0080` echoed as the last ramp
  value), plus a 15×u16 tail (`0x0880 0x0080 0x00a1 0xf8c1 0xf0e3 0xe8e3 0xe0e3
  0xe103 0xe123 0xd943 0xd965 0xd185 0xd1a5 0xd1a7 0xd1ed`) — table-shaped data
  (rate-control/threshold-like), NOT DCS/GPIO sequences;
- **no DCS bytes (0x11/0x29/0x28/0x10 as packet payloads), no GPIO numbers (144/145/160
  = 0x90/0x91/0xa0), no I2C address/register pairs identifiable.**

### 1.3 Verdict (the load-bearing negative result)

**Block 55 does not contain panel/TCON init.** It is DSC compression-parameter data
(two per-LFP entries), carried at the 198–212-era block ID, ignored by the kernel,
and the panel is plain video-mode DSI at 800×1280 (block 52: video, non-burst with sync
events, 4 lanes — DSC not in use at this resolution). The NO_CLEAN_FIX_PROOF §7.1(c)
open item "block-55 VBT table undecoded" is now **closed with a negative result**: the
missing GOP programming is not in block 55, and nothing in the runtime VBT beyond block 53
carries panel-init content (block 53 itself is fully decoded, GOP_DSI_RE_FINDINGS §2).

Tooling for the record (reproducible):
`python %TEMP%\opencode\decode_b55.py docs\dumps\re_kit\runtime_vbt.bin 52 53 55`
(script archived in this repo's research kit on demand — parser logic is 40 lines:
find `BIOS_DATA_BLOCK `, walk 3-byte headers, special-case block 53 v3, hexdump).
Device-side equivalent: `intel_vbt_decode /sys/kernel/debug/dri/*/i915_vbt`
(igt; also `intel_bios_dumper` per Intel's official VBT doc
https://drm.pages.freedesktop.org/intel-docs/vbt.html, which also lists
`/sys/kernel/debug/dri/0/i915_opregion` and the PCI-ROM dump path
`/sys/devices/pci0000:00/0000:00:02.0/rom`).

Also corrected in passing: GOP_DSI_RE_FINDINGS §2's VBT B block list ("31 32 40 41 42 43
44 46 51 52 53 55 252 253 254") is an **abbreviation** — the runtime VBT actually contains
blocks `1 2 3 6 7 8 9 10 12 13 17 18 20 26 27 28 31 32 40 41 42 43 44 46 51 52 53 55 252
253 254` (igt's own "BDB blocks present" header, `runtime_vbt_decode.txt:21-23`).

### 2.3 TCON candidates for an 10.1" 800×1280 MIPI-DSI panel (web, MEDIUM)

| candidate | why plausible | ID fingerprint |
|---|---|---|
| **AUO G101EAN01.0 / .x** | the canonical AUO 10.1" 800×1280 MIPI 4-lane module (many distributors); D330's VBT says AUO — a TN variant or successor glass most likely | DCS `0x04` (3-byte ID) / `0xDA 0xDB 0xDC`; AUO TCON IC is typically in-house — the ID triple is the discriminator |
| Ilitek **ILI9881C** | extremely common 800×1280 DSI TCON in budget GLK tablets; datasheet public (gtdisplays.com PDF) | ID via ID-page regs (`0xFF` page select then `0x00–0x02`) or DCS 0x04 |
| Sitronix **ST7701/ST7703** | common low-res portrait DSI TCONs; ST7703 datasheet public (Pine64 PDF) | DCS 0x04 / chip-ID regs |
| Himax **HX8394(F)** | common 800×1280 DSI TCON; kernel driver `panel-himax-hx8394.c` | DCS 0x04 |
| Novatek **NT36672(a)** | common in 1200×2000/800×1280 DSI; kernel driver `panel-novatek-nt36672a.c` | DCS 0x04 |

EDID is impossible on DSI (no aux/edge channel on a bare DSI panel) — identification
must go through DCS reads and/or an I2C sideband sweep. All candidates answer (or
refuse) DCS `0x04`; refusals are themselves informative.

## 3. Which I2C bus, what to probe from the live kernel (Q2 first half + Q3)

### 3.1 The I2C facts we already own (on-device VBT, HIGH)

- VBT block 52 (MIPI config): `MIPI PMIC I2C Bus Number: 6` (both VBTs;
  `runtime_vbt_decode.txt:903`), `PPS GPIO Pins: Using PMIC` — the panel rails
  (GPIO 160 reset / 144 power / 145 backlight) are **PMIC GPIOs** on a PMIC reachable
  at I2C bus index 6 in the firmware's numbering.
- VBT block 53 v3 sequences contain **only SEND_PKT (DCS), DELAY, GPIO elements** —
  **zero I2C / SPI / PMIC elements**. So per the VBT, the panel TCON is programmed
  **over DSI, not I2C**; the I2C bus 6 is the PMIC rail path, not a TCON sideband.
- The kernel's `bxt_gpio_set_value` path (`intel_dsi_vbt.c`, DISPLAY_VER ≥ 9) resolves
  GPIO **index** (0/3/4) via `devm_gpiod_get_index(dev, NULL, idx)` against the GFX
  device's ACPI `_CRS` GpioIo resources; the VBT GPIO *numbers* (160/144/145) are
  firmware-side identifiers. The GOP's rail path (I2C bus 6 → PMIC GPIO) is the
  firmware's own implementation of the same logical rails — which is why the kernel
  replays them as GPIO descriptors and never needs bus 6 (no PMIC elements in block 53).

### 3.2 Live-kernel probe commands (all no-hardware, run on the device)

```bash
# — i2c bus inventory: which buses exist, which controller each is
for d in /sys/bus/i2c/devices/i2c-*; do echo "$d $(cat $d/name)"; done
i2cdetect -l                       # i2c-tools package: apt install i2c-tools
ls -l /sys/bus/i2c/devices/i2c-6/device    # symlink → LPSS I2C PCI device (GLK)

# — sweep every bus for the PMIC (expect something on bus 6) and any TCON sideband
for n in $(seq 0 9); do [ -e /dev/i2c-$n ] && { echo "== i2c-$n"; i2cdetect -y $n; }; done

# — PMIC GPIO chip / rails (libgpiod): the rails the kernel toggles
gpioinfo | grep -iE "panel|bklt|reset|INT33FF|pmic"   # chips + claimed lines
dmesg | grep -iE "pmic|i2c_designware|gpo"             # PMIC HID + controller enumeration

# — ACPI: GFX device _CRS GpioIo resources (what index 0/3/4 resolve to)
ls /sys/bus/acpi/devices;                              # look for PMIC HID entries
acpidump > /tmp/acpi.bin && acpixtract -a /tmp/acpi.bin && iasl -d *.dat  # DSDT GFX _CRS

# — trace EVERY i2c-core transfer the kernel emits (incl. DSI-instrument era)
echo 1 > /sys/kernel/tracing/events/i2c/i2c_write/enable
echo 1 > /sys/kernel/tracing/events/i2c/i2c_read/enable
echo 1 > /sys/kernel/tracing/events/i2c/i2c_reply/enable
echo 1 > /sys/kernel/tracing/events/i2c/i2c_result/enable
cat /sys/kernel/tracing/trace_pipe                     # while suspend/resume or DCS instrument runs
# boot-time equivalent: kernel cmdline trace_event=i2c:i2c_write,i2c_read,i2c_reply,i2c_result
```

Tracepoint names verified against `include/trace/events/i2c.h` (events `i2c_write`,
`i2c_read`, `i2c_reply`, `i2c_result` on `__i2c_transfer()`). **Boundary (honest):**
these trace only i2c-core traffic. Traffic the GOP does over I2C **before** the kernel
starts is invisible to any kernel tracing — pre-kernel GOP I2C is out of reach without a
logic analyzer (consistent with the no-hardware constraint); `pm-graph`/Bootgraph profiles
timing, not bus traffic, and does not close this. What i2c tracing DOES add: confirmation
of which bus/address the PMIC sideband uses during kernel-side sequence execution, and a
guard that no panel-TCON sideband writes exist on any bus during enable.

### 3.3 DSI/MMIO probing via the existing dump node (Q3)

- Existing instrument (in CI baseline, kernel `7.0.14-d330-fix`):
  `/sys/kernel/debug/dri/*/i915_dsi_regs` — 7,296 words over the 5 locked ranges
  (0x6b000-0x6c000 DSI ports, 0x160000-0x164000 PHY, 0x46000-0x47000 clocks,
  0xc7200-0xc7400 PPS, 0x138000-0x139000 GT), PLL-gated, re-probe-safe (post-49 fix).

- No `i915_dsi_info` node exists on this kernel (and no upstream hits found either) —
  the `i915_dsi_regs` node remains the right vehicle; extend it rather than adding a new one.

## 4. The DCS ID read instrument — the concrete v10.0 next step (Q3+Q2 fused)

**Design:** extend the existing dump node's write side: `echo 2 >
.../i915_dsi_regs` performs, after the normal MMIO walk, **DCS reads against the live
DSI device** and appends them as an annotated section. Reads required:

| read | purpose |
|---|---|
| DCS `0x04` (Get Display ID, 3 B) | ID1 ID2 ID3 — the TCON fingerprint (MIPI DCS standard) |
| DCS `0xDA`, `0xDB`, `0xDC` (1 B each) | ID1/ID2/ID3 fallback — many TCONs answer these when 0x04 is unimplemented |
| generic read request (type 0x83, reg 0x00) | some TCONs expose a register page via generic packets |

Implementation facts that make this cheap (all verified in mainline source):

- `mipi_dsi_dcs_read()` → `intel_dsi_host_transfer()` (`vlv_dsi.c`) **implements the RX
  path**: it arms `MIPI_INTR_STAT` for `GEN_READ_DATA_AVAIL`, waits for the interrupt,
  then `read_data()` from the LP/HS GEN DATA register. Reads are supported on GLK.
- **BTA is enabled** on the D330: VBT block 52 `BTA disable: Disabled`
  (`runtime_vbt_decode.txt:841`) — bus turnaround for reads is permitted.
- The VBT sequence executor itself **cannot** do this: `mipi_exec_send_packet()` returns
  `-EOPNOTSUPP` for all READ packet types (`intel_dsi_vbt.c`) — a read instrument must
  call `mipi_dsi_dcs_read()` directly, which is why it needs the node extension.
- Mode: issue reads in **LP mode** (`MIPI_DSI_MODE_LPM`), VC 0, port A (single-link
  DSI; `intel_dsi_seq_port_to_port` forces port A when hweight8(ports)==1).

**Capture protocol (mirrors the 47/49 discipline):** boot arm (image showing, X=Y) +
resume-black arm (X=Z) + optionally after the panel-power-cycle candidate — the same
`echo 2` node call, registered in the kit (`MANIFEST.sha256`), diffed. If ID reads
succeed at boot but fail/hang at wake, that directly evidences TCON state loss; if they
succeed in both states, the TCON is alive-but-misconfigured and the hunt pivots to its
wake-register content (then map reads to the identified datasheet).

**Expected payoffs:** (1) TCON identity → public datasheet → documented wake/reset
requirements (the "panel TCON datasheet" gap named in v9.0's audit, obtained software-only);
(2) AUO product-code cross-check (PnP 6104 vs live ID); (3) an I2C-sideband sweep in the
same session rules the sideband in or out.

## 5. What the GOP programs that the kernel cannot — executor analysis (Q4)

### 5.1 The executor is complete for THIS VBT

`drm/i915`'s MIPI sequence executor (`intel_dsi_vbt.c`) supports every element type the
VBT spec defines (`exec_elem[]`: SEND_PKT, DELAY, GPIO, I2C, SPI, PMIC), and the D330's
block 53 v3 uses only SEND_PKT/DELAY/GPIO — **nothing in the D330's VBT is unimplemented**.
The executor did not fail to "miss" a sequence: it ran every element (ftrace-proven,
RESUME_VS_RELOAD_DIFFERENTIAL diag44 trace), and the panel still cannot show an image
at resume while boot (GOP) shows X=Y.

Upstream's own enable-order diagram (`vlv_dsi.c` comment, "Panel enable/disable sequences
from the VBT spec") matches the traced kernel behavior; the GOP's divergence must be in
what it does **outside** block 53:

1. **The GOP's own link bring-up** (mode set + DPHY config outside the VBT's timing
   tables). The strongest candidate: the DPHY calibration area 0x162000-0x164000
   (IREF/GRC) reads all-ones on every arm through the in-kernel path (DSI_MMIO_DIFF
   §4.3) — the GOP's PHY-calibration writes are invisible to readback, and the kernel's
   replay writes the same ftrace-known words (0x162024=8080e480, 0x162028=8080e480,
   0x162070=33cb0443) — so value-level divergence there is unprovable from readback.
2. **Panel-side state reachable only by the GOP's exact cold sequence** — consistent with
   the X=Y/X=Z operational contrast + forced-X=Y-insufficient (v8.0 row 18).
3. **`IntelGraphicsMem` NVRAM state** (GOP var at `gop_driver_dc90d1e2.efi` offset 0x4a40,
   GOP_DSI_RE_FINDINGS §3.1) — the GOP's save/restore state machine may carry TCON-side
   state that a plain re-init never reconstructs.

### 5.2 Register-name map for the X=Y/X=Z rows (from `vlv_dsi_regs.h`, HIGH)

| offset | tree name | boot (X=Y) | broken (X=Z) | reading |
|---|---|---|---|---|
| 0x6b004 | `MIPI_INTR_STAT(A)` | 00080000 | 40280000 | **W1C status — decode: bit30 `SPL_PKT_SENT_INTERRUPT` + bit21 `HS_TX_TIMEOUT` + bit19 `LOW_CONTENTION`. NOTE: bit22 `LP_RX_TIMEOUT` is NOT set — DSI_MMIO_DIFF §6's "LP_RX_TIMEOUT-marked" label is imprecise and should be corrected** |
| 0x6b010 | `MIPI_HS_TX_TIMEOUT(A)` | 003fffff | 0000b8ea | kernel writes `txbyteclkhs(vtotal·htotal, 24bpp, 4lanes)+1 ≈ 0xEF8AA` in non-burst vid mode (`vlv_dsi.c:1402-1408`) — **0xb8ea matches neither the kernel's computed value nor the GOP/VBT 0x3fffff: open probe question (read-after-write check)** |
| 0x6b044 | `MIPI_HIGH_LOW_SWITCH_COUNT(A)` | 0000001d | 0000001e | LP→HS switch count |
| 0x6b080 | `MIPI_DPHY_PARAM(A)` | 09051003 | 0a051003 | exit_zero 9→10, trail 5, clk_zero 0x10, prepare 3 — VBT wants exit_zero 0x3f (`runtime_vbt_decode.txt:868`); boot matches neither |
| 0x6b088 | `MIPI_CLK_LANE_SWITCH_TIME_CNT(A)` | 0022000f | 0014000c | lp_hs_ssw 0x22→0x14, hs_lp_pwr 0xf→0xc |
| 0x6b094 | `MIPI_INTR_EN_REG_1(A)` | 00000001 | 00000000 | `RX_CONTENTION_DETECTED` enable dropped |
| 0x6b098 | `MIPI_CLK_LANE_TIMING(A)` | 09051003 | 0a051003 | clk-lane timing counts |
| 0x6b104 | `MIPI_CTRL(A)` (RO bits) | d0000003 | d0000003 | PHY ready + ULPS-not-active + MIPIIO powered — **identical, not a discriminator** |
| 0x160018 | (unnamed PHY ctrl) | 00000115 | 00000001 | bits 8/4/2 cleared only on broken |
| 0x160084 | (unnamed PHY) | 000003fc | 00000000 | boot-to-boot variance (s1 boot also 0) — not a signature |

**Mechanism reading the names sharpen:** in the broken state the DSI host's status
shows `HS_TX_TIMEOUT` + `LOW_CONTENTION` — the host tried to run the HS video stream and
the far end (panel TCON) never took it. That is exactly a **TCON-side** signature,
matching the corrected mechanism statement (DSI_MMIO_DIFF §5.2, NO_CLEAN_FIX_PROOF §7.1):
the image requires the GOP's full panel init including its direct TCON programming.

Honest anomalies to flag for the phase (do not paper over):
- session-1 working resume held `0x6b010=003fffff` — under a full kernel enable that
  should read the computed value; either that enable aborted before timer programming
  or the register self-modifies. The §5.2 probe (write/read-back check) resolves it.
- `0x6b080` boot (0x09 exit-zero) matches neither GOP-referenced VBT values (0x3f) nor
  kernel defaults — DPHY_PARAM may be partially self-updating on GLK.

## 6. Recommended v10.0 phase shape (for the roadmap)

1. **Phase A — TCON identification (the §4 instrument):** extend `i915_dsi_regs` with
   DCS ID reads (`echo 2` trigger), one CI build, boot + black-resume captures,
   eyes-on + kit-registered. Deliverable: TCON identity or a proven read-path dead end.
2. **Phase B — depending on A:** if TCON identified → datasheet-gated wake-requirement
   candidates (the ladder); if reads dead → pivot to the I2C sweep results (sideband?)
   and the 0x162000+ write-replay question with the write/read-back probes (§5.2).
3. **Phase C — close-out:** correct DSI_MMIO_DIFF §6's `0x6b004` label (bit-level decode
   above), register the new captures, honest verdict per the ≤5-iteration ledger rule.

## 8. The 10 load-bearing facts

1. **Block 55 = DSC compression parameters (old format, BDB 198-212)** — kernel never
   parses it; not the panel-init table; "block-55 mystery" closed as a negative result.
2. **Panel glass maker = AUO** (VBT block 42 PnP ID, mfg 0xaf06, product 6104) — the first
   vendor attribution for the TCON hunt; date field template-suspect.
3. **Lenovo display FRU = 5D11A20220** ("LCD MODULE H 82H0 10.1 HD Touch"); bare glass not
   publicly cross-referenced → DCS ID read is the closing instrument.
4. **DCS ID read instrument is feasible software-only:** `mipi_dsi_dcs_read()` works
   through `intel_dsi_host_transfer()` (RX implemented) and **BTA is enabled** (block 52).
5. **The VBT executor implements 100% of the D330's block 53** (no I2C/SPI/PMIC elements
