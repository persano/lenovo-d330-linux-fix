# v10.0 Research: Black-Resume Self-Healing Safety Net

**Project:** lenovo-d330-linux-screen-fix (Lenovo IdeaPad D330-10IGL, 82H0, Gemini Lake, i915 GLK DSI panel)
**Mode:** ecosystem/design research for milestone v10.0
**Ground truth inherited:** v9.0 audit (honest closure — fix unreachable from the kernel), RESUME_FIX_LEDGER rows 1-32 (binding), RESUME_VS_RELOAD_DIFFERENTIAL, phase-49 eyes-on close-out.
**Scope note:** this is MITIGATION TOOLING, not a panel fix. It re-proposes no ledger lever; its only recovery action is the one action the ledger's proven bar blesses: **reboot**.

---

## 1. The problem the safety net must solve

After S3 resume the panel shows no image. Two observed shapes:

1. **Dark resume** (idle screen-off before suspend): connector left disabled, backlight off (`bl_power=4` post-resume; re-enabling gives lit-black).
2. **Lit-black resume** (screen ON before suspend): the full VBT enable path runs, DCS writes complete, backlight on — no video stream displays.

And since phase 49 (eyes-on, 3 cycles): **every userspace-observable recovery is insufficient** — the unbind/bind reload leaves lit-black (kwin dies on unbind, the pipe is never re-driven; sddm restart too). The only action that ever restored a visible image is a **full reboot** (it re-runs the GOP's firmware panel init, which is unreachable from every kernel path tested).

So the device reality until a real fix lands: *user resumes → panel may be black → user must know to reboot.* The safety net's job: detect that moment, warn, and reboot cleanly — with guardrails so it never reboots a working session.

---

## 2. The 10 most load-bearing facts

1. **Reboot is the only proven recovery** (ledger proven bar + row 29 re-confirmed eyes-on in phase 49 on the v9.0 kernel). The unbind/bind reload restores *sysfs* state, never the visible image; sddm restart too. Nothing else (bare reset, remove-and-re-enumerate tricks, lighter levers) recovers the panel.

2. **No host-side readout discriminates "image" from "black".** The v9.0 falsification chain: DSI block MMIO 0x6b000-0x6c000 bit-identical (1024/1024) between the image-showing and black states; `i915_display_info` byte-identical boot-vs-resumed while dark; the failure is below host MMIO (panel TCON side). Machine detection from kernel state is a dead end **by construction**, not by lack of effort.

3. **The X=Y/X=Z MMIO contrast cannot be the safety net's detector.** It discriminates fresh-boot-image (X=Y) from every broken state (X=Z, held indefinitely, re-probe included), but (a) it exists only on the 47/48 dump kernel (instrument branch, 11 commits, unmerged — not the production kernel v10.0 must serve), and (b) no working *post-resume* sample exists to define a green signature — the contrast classifies, it cannot confirm "image currently visible".

4. **Sysfs panel state proves nothing about the visible outcome** (ledger proven bar, myth-busted with eyes-on). `enabled=enabled dpms=On bl_power=0` was recorded while the panel showed nothing. Any detector built on `/sys/class/drm/*` or backlight files would be silent theater.

5. **Pipe CRC (and any scanout/vblank counter) is host-side only.** From kernel source `display/intel_pipe_crc.c`: the CRC is computed inside the display engine (`PIPE_CRC_CTL`), upstream of the DSI link; a lit-black panel whose TCON died still scans out a changing desktop → valid changing CRCs; capture while the pipe is off returns `-EIO`; and enabling CRC performs an internal atomic commit (it perturbs the state you are trying to observe). Rejected for detection.

6. **The user's eyes are the only working detector — so the design makes "eyes" an API.** The repo's own method already accepts only eyes-on verdicts for panel outcomes (every iteration log says so). A deliberate user hotkey ("screen is black — recover") is the same epistemology turned into a trigger: zero false positives, works for both black shapes, and is the recommended primary trigger.

7. **Plasma 6 supports command shortcuts natively.** KHotKeys was removed in Plasma 6 (never worked on Wayland). Replacement: System Settings → Shortcuts → Add New → **"Command or Script…"** (KCM, Plasma 6.1+, executed by kglobalacceld, Wayland-safe). Binding Meta+Shift+B → `sudo -n /usr/local/bin/d330-blackguard --trigger` is a one-time settings step, no new daemon. (KDE bug 489529 documents the exact flow.)

8. **Root can watch the keyboard without any graphical session.** `struct input_event` is 24 bytes on x86-64 (16-byte timeval + u16 type + u16 code + s32 value, `include/uapi/linux/input.h`); a root script reading `/dev/input/eventN` gets raw EV_KEY activity with kwin, sddm and kglobalaccel dead. This is what makes the guardrails (pause while typing, Esc cancels) and the keys-heuristic mode session-independent.

9. **Post-resume hook points in systemd are exactly two.** (a) `/usr/lib/systemd/system-sleep/` — runs with `post <action>` after wake, synchronously, in parallel, blocking the suspend transaction until done; `user.slice` is frozen while hooks run (so the hook must spawn a detached child and exit fast; systemd calls hooks "local-use hacks"); (b) the official `sleep.target` recipe — oneshot `WantedBy=sleep.target`, `Before=sleep.target`, `RemainAfterExit=yes`, `StopWhenUnneeded=yes`, post-wake command in `ExecStop=`. There is **no** `resume.target`; `systemd-hibernate-resume(.service/@.service)` only initiates resume *from hibernation* (writes major:minor to `/sys/power/resume`) — the "systemd-resume.service" hook candidate from the brief is a dead end for S3.

10. **The existing display resume hook is now strictly harmful and must stand down.** `patches/display/etc/systemd/system-sleep/lenovo-d330-display-resume.sh` unbinds i915 (kwin dies, session lost) then restarts sddm — and per fact 1 the panel comes back lit-black anyway. Post-v9.0 it destroys the session for zero visual gain. It ships its own disable mechanism (`/etc/default/lenovo-d330-display-resume`, `D330_DISPLAY_RESUME=0`) and coexistence contract (`D330_REAL_FIX=1`); the v10.0 installer must write the disable file and say why in the journal.

## 3. Detection design — options evaluated

**The discriminator problem.** The detector must output a binary verdict: "image gone" vs "image fine". Facts 2-5 remove every machine signal:

| Option | Mechanism | Verdict | Why |
|---|---|---|---|
| (a) DRM fbdev/pipe state, scanout frame counters, pipe CRC | read display-engine state | **REJECTED** | All host-side (fact 5). Lit-black still scans out; dark pipe reads `-EIO` but sysfs state already proved not to imply image loss (fact 4). CRC enable perturbs state. Dump-node X=Y/X=Z contrast not available on production kernel and can't certify "visible now" (fact 3). |
| (b) Keyboard heuristic — no visual feedback N s after resume + user types | root evdev burst counter during armed window | **Viable, opt-in, default OFF** | Works with wedged session (fact 8). False positive: user typing at a *visible* lock screen / TTY → would reboot a working panel. Mitigated by countdown + pause + Esc, but the default must stay `hotkey` because a false reboot is worse than a manual reboot. If enabled, filter to EV_KEY-only devices (exclude devices with EV_ABS / BTN_TOUCH so the touchscreen can't arm it — one on-device probe task to confirm the D330's touch/digitizer node split). |
| (c) User hotkey/shortcut — "confirm black, recover" | Plasma 6 command shortcut → sudo -n trigger file | **RECOMMENDED primary** | Human-confirmed (fact 6), zero false positives, one settings step (fact 7). Fallback path when kglobalaccel is somehow dead: the `keys` mode or a second trigger — plain `sudo /usr/local/bin/d330-blackguard --trigger` from a VT (works headless). |
| (d) KDE/sddm session state after resume | process liveness, loginctl | **REJECTED as detector; useful as aux signal** | kwin runs fine while the panel is lit-black; session state cannot see the panel. Only marginal use: if sddm/kwin *crashed* on resume that is a different failure — log it, don't reboot for it. |

**Recommended detection stack:** `hotkey` primary + `keys` opt-in; every trigger funnels into the same guarded countdown. No kernel readouts anywhere in the critical path — that is the design's honesty: the safety net does not pretend the machine can see the panel.

## 4. Recovery ladder and the auto-reboot flow

Ranked by destructiveness, with ledger row numbers:

| Action | Verdict | Row |
|---|---|---|
| Backlight re-enable / DPMS cycle | Insufficient — lit-black, second bug | 27 |
| Compositor re-drive (KScreen DPMS cycle) | Insufficient — dpms stuck Off | (45-02 iter 4) |
| Display-manager restart (sddm) | Insufficient — lit-black; also kills the session | phase 49 |
| Full i915 unbind/bind reload | Insufficient — lit-black (re-confirmed eyes-on); destroys session | 29 |
| Module unload | Impossible — module in use | 13 |
| **Reboot** | **Proven — re-runs GOP firmware panel init** | proven bar |

**Flow (single path, no branches on kernel state):**

```
resume completes
  └─ hook post → DMI gate (82H0) → config gate → spawn detached child → hook exits (fast)
       child: settle 15 s (user.slice thaw, session back)
       arm window (default 900 s):
         trigger = trigger file (hotkey) ∨ evdev burst (keys mode, opt-in)
       on trigger:
         log "black suspected" to journal (t=d330-blackguard)
         beep ×1 (paplay → pw-play → logger only)          [audio works when panel can't]
         countdown 10 s:
           any EV_KEY in last 1.5 s  → pause countdown (never reboot mid-typing)
           Esc                       → cancel, log, disarm
           beep each second
         at 0 s:
           journal marker "AUTO-REBOOT: black resume" (timestamp, config sha, trigger source)
           systemctl reboot
```

`systemctl reboot` is called from the detached child (not from inside the hook — the manager is busy inside the sleep transaction while hooks run; a synchronous systemctl call from a hook risks blocking the resume). The child runs outside the frozen `user.slice` window once the settle delay passes.

Why the 10 s warning is not theater even on a black panel: the beeps land on the *speakers*, not the screen; the journal lands for post-reboot forensics (which trigger, which config, paused how many times); and in the false-positive case (panel actually fine) the user sees/hears the countdown and hits Esc.

## 5. Hook placement decision

| Candidate | Verdict |
|---|---|
| `/usr/lib/systemd/system-sleep/` hook (pre/post) | **CHOSEN.** Matches the repo's existing hook house style (wifi, touchscreen, display hooks live there); pre/post covers kill-and-clean + spawn; officially supported for local use (the man page's "hacks" caveat is about app integration, not admin tooling). |
| systemd-suspend.service drop-in ExecStartPost | Rejected — drop-ins on packaged units are fragile across systemd updates; same effect as the hook with more machinery. |
| `sleep.target` ExecStop recipe (`RemainAfterExit=yes StopWhenUnneeded=yes`) | Documented official alternative (systemd.special man, with example unit). Valid second choice; unit-based (journal-friendly). Note for the planner: the unit file mentioning `sleep.target` is legitimate tool wiring, not the row-22 masking lever — keep a narrow `planner-discipline-allow: sleep.target` marker in any scanned plan that quotes it. |
| `systemd-resume.service` / a `resume.target` | **Does not exist for S3.** `systemd-hibernate-resume*` units are hibernation-image resume only (initrd, writes to `/sys/power/resume`). Dead end; remove from consideration. |
| Desktop shortcut alone (kwin/kde) | Rejected as the *hook* (depends on a live graphical stack); kept as the *trigger* UI (fact 7). |

**Architecture of the chosen path (detached-child pattern):**

```
/usr/lib/systemd/system-sleep/lenovo-d330-blackguard.sh     (hook: pre=cleanup, post=spawn)
/usr/local/bin/d330-blackguard                              (state machine: arm/trigger/countdown/reboot)
/run/d330-blackguard/armed, trigger, quiet, lock            (tmpfs state, TTL'd)
/etc/default/lenovo-d330-blackguard                         (config + master disable)
```

## 6. Guardrails specification

1. **Never reboot mid-typing.** During countdown, the child reads evdev directly (root, no session dependency — fact 8). Any EV_KEY event within the last `IDLE_CANCEL_MS` (default 1500 ms) freezes the remaining countdown; typing resumes it after `IDLE_CANCEL_MS` of quiet. This satisfies "the trigger is typing" (keys mode) while "keep typing" always wins.
2. **Explicit cancel.** Esc cancels unconditionally (also from inside a pause). Documented on-device: *Esc = no, wait = pause, do nothing = reboot in 10 s*.
3. **Debounce / single instance.** `flock` on `/run/d330-blackguard/lock`; one armed window per resume (`/run/d330-blackguard/armed` carries the wake epoch); the hook's `pre` phase kills the child and clears state (lid close / second suspend mid-window cannot leave a stale timer).
4. **Arm window TTL.** The child self-expires after `ARM_WINDOW_S` (default 900 s) — no trigger that long after resume is about this bug; disarm and log.
5. **Master disable + per-case disable.** `/etc/default/lenovo-d330-blackguard`: `D330_BLACKGUARD=0` disables everything (hook logs it on every resume, house pattern from the display hook); `DRY_RUN=1` runs the full state machine and logs "would reboot" instead of rebooting. Removal of the hook file is always the nuclear off.
6. **Works wedged.** No step after the hook depends on the graphical session: trigger file can also be written from a VT; evdev is read directly; reboot goes through the system manager. The KDE shortcut is a convenience input, never a dependency.
7. **Research-session quiet mode.** rtcwake capture sessions (`close_session_d330.sh` pattern) intentionally produce black panels. The arm child refuses to countdown while `/run/d330-blackguard/quiet` exists (TTL'd file, e.g. 10 min); the capture helper/installer writes it. Requirement for v10.0: extend the capture helper (or document the manual `touch`) so automated sessions can never self-reboot mid-capture.
8. **Forensic trail.** Every decision logged `logger -t d330-blackguard`: arm, trigger (source: hotkey|keys|vt), pauses, cancel, reboot marker with pre-reboot uptime and suspend elapsed. Post-reboot, `journalctl -t d330-blackguard -b -1` answers "was this an auto-reboot?".

## 7. Repo integration plan (house style followed)

**Ship tree** (mirrors device paths, like `patches/display/etc/systemd/system-sleep/…`):

```
patches/blackguard/
  usr/local/bin/d330-blackguard                          # state machine (bash, ~200-300 lines, python3 optional)
  usr/lib/systemd/system-sleep/lenovo-d330-blackguard.sh # hook (sh, house style of the display hook)
  etc/default/lenovo-d330-blackguard                     # config defaults
  etc/sudoers.d/d330-blackguard                          # NOPASSWD exact-command grant
  README.md                                              # the KDE shortcut how-to (Add New → Command or Script…)
scripts/install_blackguard_d330.sh                       # host-side installer → santiago-D330
scripts/test_blackguard.sh                               # deviceless test harness
```

**Installer conventions** (copied from `deploy_d330_kernel.sh` + `capture_dsi_dumps.sh`):
- device alias `santiago-D330` (override `D330_DEVICE`/`D330_SSH_OPTS`, same env contract); credential discipline: `D330_SUDO_PW` env → hidden prompt → stdin line, piped only into `sudo -S -p ''`, never logged.
- staged via scp to `/home/santiago/`, **uploaded copies sha256-verified on device before install** (the deploy script's scp-corruption guard).
- installs: binaries to `/usr/local/bin`, hook to `/usr/lib/systemd/system-sleep/` (mode 0755), config to `/etc/default/`, sudoers drop-in validated with `visudo -c` before activation, `chmod 0440` (sudoers.d files are skipped by sudo if the name contains `.` or ends `~` — name is `d330-blackguard`, no dots).
- writes `/etc/default/lenovo-d330-display-resume` with `D330_DISPLAY_RESUME=0` and journals why (fact 10) — the legacy reload hook stands down via its own documented mechanism.
- `DRY_RUN=1` skips all ssh/scp (deploy-script precedent).

**Sudoers grant (minimal):**

```
santiago ALL=(root) NOPASSWD: /usr/local/bin/d330-blackguard --trigger
```

Exact path + exact argument. Abuse ceiling: a forced countdown with a 10 s Esc-cancel — acceptable on a single-user tablet. Alternative documented but not chosen: polkit rule scoping `org.freedesktop.systemd1.manage-units` to one `d330-blackguard-trigger.service` unit (more moving parts: dbus + rules.d JS).

**KDE shortcut (documented, one-time, manual):** System Settings → Shortcuts → Add New → **Command or Script…** → `sudo -n /usr/local/bin/d330-blackguard --trigger` → assign Meta+Shift+B. (Scripting `~/.config/kglobalshortcutsrc` is fragile across Plasma 6 minor versions — left manual; a `.desktop` launcher with `X-KDE-Shortcuts=` is the fallback variant if automation is later required.)

**Tests (`scripts/test_blackguard.sh`, repo harness style):** mock `/sys/class/dmi/id/product_name`, fake config files, and a fixture evdev stream (synthetic 24-byte `input_event` records) piped to the state machine in DRY_RUN. Assertions: DMI gate rejects non-82H0; disable file wins; trigger → countdown; key burst → pause; Esc → cancel; TTL expiry; flock prevents double-arm; DRY_RUN never emits `systemctl reboot`; quiet file suppresses countdown.

**Optional future:** keys-heuristic tuning (burst length, EV_ABS exclusion) needs one on-device probe of the D330's input node split — flagged as a phase-specific research item, not a blocker.

## 8. Anti-features (explicitly NOT built)

| Anti-feature | Why not | Instead |
|---|---|---|
| Machine "black detector" (CRC / frame counters / sysfs math) | Host-side signals proven blind to the failure (facts 2-5); a fake detector is worse than none | Human-confirmed trigger + opt-in heuristic |
| Re-propose any reload/rebind variant inside the net | Row 29; also kills the session | Hook stands the legacy reload down |
| Auto-reboot without countdown | One wrong trigger = lost work | 10 s + beeps + Esc + pause-on-typing |
| Watching kwin/sddm health to decide | Cannot see the panel (fact 4); liveness ≠ image | Log-only aux signal |
| Camera-based "is it black?" vision probe | Privacy, wedged-camera risk, ambient-light flakiness, new failure modes | — |
| Persistent daemon | Hook + TTL'd tmpfs state covers it; a daemon is one more thing to wedge | Detached child per resume |

## 9. Risks / open questions

- **keys-mode false positive** (typing at a visible screen arms a reboot): default OFF; countdown pause + Esc + beeps are the mitigation; require explicit user opt-in with the trade-off stated.
- **kglobalacceld availability**: if the shortcut daemon dies the hotkey dies; acceptable (VT + manual command remain), noted in README.
- **`sleep.target`-recipe alternative** is cleaner unit-wise but less battle-tested in this repo than the hook pattern; the hook is the v10.0 baseline, the recipe is documented as the fallback if systemd ever deprecates hooks.
- **Settle delay tuning** (15 s): too short → trigger before user.slice thaw; too long → user stares at black with no arm. Make it config; measure once on device.
- **Phase-specific research flags:** keys-mode device probe (input node split); kglobalshortcutsrc automation only if the manual step is a real adoption blocker.
