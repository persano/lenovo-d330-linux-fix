# Keep-Panel-Powered Through S3 — Research Findings (v10.0)

**Research question:** the kernel cannot re-init the panel after it powers off (v8.0+v9.0: 31+ ledger rows, every kernel path lands at X=Z, only GOP boot init reaches X=Y, recovery = reboot). Can we stop the power-off from happening at all — hold panel power rails / backlight / DSI link hot through S3 so the TCON never loses its GOP-set init state, and the resume path never needs to re-init the panel?

**Sources grounded this session:** raw `torvalds/linux` tag `v7.0` (vlv_dsi.c, intel_dsi.c, intel_dsi_vbt.c, intel_display_power.c, intel_display_driver.c, intel_display_params.c, intel_pps.c grep), `chromium.googlesource.com` chromeos-5.4 / chromeos-5.15 `vlv_dsi.c`, plus the repo's own machine evidence (DSI_MMIO_DIFF §5.2, NO_CLEAN_FIX_PROOF §7/§7.1, DSI_RESUME_TRACE_ANALYSIS, GOP_DSI_RE_FINDINGS, v9.0-MILESTONE-AUDIT). Web search API (brave) was unavailable; secondary-web claims are flagged LOW and listed as gaps.

---

## The 10 most load-bearing facts

1. **The suspend panel power-off is exactly three VBT sequence calls plus one DCS command, all in `intel_dsi_post_disable()` (vlv_dsi.c:868-932):** `MIPI_SEQ_DISPLAY_OFF` (line 901, DCS 0x28 + 0x10), host-side link teardown (`intel_dsi_clear_device_ready`, 904 → GLK ULPS enter + MIPI IO power-gate, 509-555), `MIPI_SEQ_ASSERT_RESET` (926, GPIO 160 low), `msleep(panel_off_delay)` (928), `MIPI_SEQ_POWER_OFF` (929, GPIO 144 low). `intel_dsi_disable()` (831) runs `MIPI_SEQ_BACKLIGHT_OFF` (842) + a video-mode SHUTDOWN DCS (853). Suspend reaches these via `intel_display_driver_suspend()` → `drm_atomic_helper_suspend()` (intel_display_driver.c:692).
2. **The full panel power cycle ALREADY happens on every S3** (source-verified + ftrace-verified: suspend runs BACKLIGHT_OFF → DISPLAY_OFF → ASSERT_RESET → POWER_OFF; resume runs POWER_ON → DEASSERT_RESET → INIT_OTP → DISPLAY_ON → BACKLIGHT_ON — DSI_RESUME_TRACE_ANALYSIS.md:170-171). v10.0's lever is the *inverse of the falsified rows 30-32*: instead of tearing down even harder, don't tear the panel down at all.
3. **Host-side MMIO cannot be held across S3 — proven from source.** On GLK, `intel_display_power_suspend_late()` (intel_display_power.c:2258-2272) unconditionally runs `bxt_display_core_uninit()` + `bxt_enable_dc9()` (line 2264); the s2idle escape hatch (2101-2142) does not apply because GLK allows DC9. The display die is power-gated through every sleep, including s2idle (which is why s2idle failed too, NO_CLEAN_FIX_PROOF row 3). Only the **external PMIC panel rails** (GPIO 144, VBT: "PPS GPIO Pins: Using PMIC", PMIC I2C bus 6) are outside that well — those are the only thing a kernel patch can hold.
4. **What the kernel can actually hold = panel-side GPIO states:** skip `DISPLAY_OFF` (TCON never told to sleep), skip `ASSERT_RESET` (GPIO 160 stays high — holding reset low would hold the TCON in reset even with rails hot), skip `POWER_OFF` (GPIO 144 stays high). Keep BACKLIGHT_OFF (backlight off through S3 is correct). Host-side teardown (ULPS, port power-gate, PLL off) must stay — DC9 wipes it anyway and the resume path expects a clean state.
5. **Resume enable is re-run by KWin's modeset ~3 s after wake, not by i915's own resume** (marker-trace proof, DSI_RESUME_TRACE_ANALYSIS.md:150-157). With no compositor it never runs. Any keep-hot patch must therefore key off panel state (a driver flag), not off "which caller".
6. **Chrome OS did NOT build this.** chromeos-5.4 and chromeos-5.15 `vlv_dsi.c` contain no DMI quirk, no keep-alive patch; `MIPI_SEQ_POWER_OFF` sits at post_disable exactly as mainline (5.4:995, 5.15:1011-1013). There is no upstream or Chrome OS precedent to copy — and no known case of Chrome OS keeping GLK DSI panels hot across S3 in kernel code (branches checked: 5.4, 5.15).
7. **Windows does re-init every S3 resume and works** (igdkmd64.sys `SB_SAVESTATE_ARGS`/`SB_RESTORESTATE_ARGS`, `GEN9DSICONTROLLER_SetTiming` — GOP_DSI_RE_FINDINGS §4): the TCON init Windows re-runs includes direct TCON programming beyond the VBT block-53 sequences. Linux re-running the VBT sequences lands at X=Z. **Keep-hot is the only kernel-side lever that does not require replicating the GOP's TCON-level init** — if the TCON never loses power/reset, there is nothing to re-init.
8. **`i915.disable_power_well=0` cannot help** — source-verified: it only keeps power wells on at runtime PM; suspend still deinits the display core and enters DC9 unconditionally (intel_display_power.c:2127-2137, 2262-2264). Dead end, do not spend an iteration on it.
9. **Experiment (d) "defer panel power-down to the resume path" is already falsified.** Row 31 (full panel power cycle at top of `intel_dsi_pre_enable`, reload-scale hold) → "black but lit", X=Z unchanged; the v8.0-era early power-cycle patch made things worse (modeset failed). The surviving reinterpretation of (d) is the **warm-resume enable**: skip `POWER_ON` + `INIT_OTP` at pre_enable when the keep-hot flag is set, keep `DISPLAY_ON`/`BACKLIGHT_ON` (VBT DISPLAY_ON = DCS 0x11 exit-sleep + 0x29 — the panel's own wake protocol).
10. **Success is measurable with the existing instrument chain, one binary criterion:** at-wake `i915_dsi_regs` dump (capture script + ≥18 s window discipline unchanged) shows the X=Y operational set — `0x6b010=003fffff, 0x6b044=0000001d, 0x6b080/0x6b098=09051003, 0x6b088=0022000f, 0x6b094=1, 0x160018=00000115` — after the re-enable commit, plus eyes-on image. D330SEQ/D330GPIO ftrace must show POWER_OFF absent at suspend (E1) and POWER_ON/INIT_OTP absent at resume (E2). X=Z or black = falsified (rails were cut anyway). Two dumps per session: ~0-1 s post-exit (pre-commit, expect DC9 reset defaults) and ~4 s post-exit (post-KWin commit, the discriminator), both inside the window.

## 1. Where panel power is cut at suspend (kernel 7.0, exact sites)

### Call chain (deep S3, compositor present)

```
suspend: i915 suspend ops
  → intel_display_driver_suspend()                       intel_display_driver.c:684
      → drm_atomic_helper_suspend()                        :692  (full atomic disable commit)
          → intel_dsi_disable()                            vlv_dsi.c:831
              MIPI_SEQ_BACKLIGHT_OFF   → GPIO 145 low      :842
              intel_backlight_disable()                    :843
              SHUTDOWN DCS (vid mode)                      :850-855
          → intel_dsi_post_disable()                       vlv_dsi.c:868
              MIPI_SEQ_DISPLAY_OFF (DCS 0x28, 0x10)        :901
              intel_dsi_clear_device_ready()               :904
                glk_dsi_enter_low_power_mode()  ULPS enter :509-534
                glk_dsi_disable_mipi_io()       IO reset+off:536-555
              bxt_dsi_pll_disable()                        :917
              MIPI_SEQ_ASSERT_RESET → GPIO 160 low         :926
              msleep(panel_off_delay)                      :928
              MIPI_SEQ_POWER_OFF → GPIO 144 low            :929
              panel_power_off_time = now                   :931
  → intel_display_power_suspend_late()                   intel_display_power.c:2258
      → intel_power_domains_suspend()                    :2101  (bxt_display_core_uninit :2137)
      → bxt_enable_dc9()                                 :2264  (display die power-gated)
```

Notes:
- `intel_dsi_unprepare()` (1509) early-returns on GLK (1515-1516) — no extra teardown on this machine.
- The broxton-only `BXT_P_CR_GT_DISP_PWRON`/DSI-regulator block (906-914) is **skipped on GLK** — the fact that motivated failed iteration 3 (MIPIO reset pulse).
- The DSI encoder has **no `.suspend` hook** in 7.0 (wiring at 1938-1947; `.shutdown = intel_dsi_shutdown` only waits the power-cycle delay, intel_dsi.c:26-31). All suspend teardown flows through the atomic disable commit.
- Panel rails/backlight/reset are **not PPS registers**: the legacy PPS block 0xc7200-0xc7400 read byte-identical on all arms (DSI_MMIO_DIFF §4, 128/128) and the ftrace proves the pins are driven by VBT GPIO sequence elements → `bxt_gpio_set_value()` (intel_dsi_vbt.c:312-316) → `soc_gpio_set_value()` (SoC pinctrl pad) → PMIC rail. The `gpio_panel`/`gpio_backlight` gpiod descriptors (intel_dsi_vbt.c:689-699) are NULL on this machine (ftrace D330GPIO, DSI_RESUME_TRACE_ANALYSIS "Update" section).
- **Resume enable** (for reference, E2's patch site): `intel_dsi_pre_enable()` 723-817 — `intel_dsi_wait_panel_power_cycle()` 737 (enforces the 5000 ms VBT cycle delay, intel_dsi.c:13-24), PLL re-enable 745-751, `MIPI_SEQ_POWER_ON` 772 (GPIO 144 high), `DEASSERT_RESET` 774 (GPIO 160 high), `glk_dsi_enable_io()` 777 (cold-boot probe, DEVICE_READY test 360-366), `intel_dsi_device_ready()` 785 (GLK ULPS dance 369-429), `MIPI_SEQ_INIT_OTP` 792 (GPIO 160 1/0/1 = **TCON reset toggle**), `MIPI_SEQ_DISPLAY_ON` 810 (DCS 0x11 + 0x29), port enable 812, backlight 815-816.

### The suspend-only discriminator (needed by every experiment)

`intel_dsi_post_disable()` runs for **every** modeset/DPMS-off, not just suspend. None of the three failed patches needed a suspend discriminator (they gated on the resume window `power.domains.init_wakeref`); the keep-hot patches gate on the **suspend** side, which has no existing flag at encoder-hook time. Design: add one bool to `struct intel_display` (e.g. `suspend_commit_in_progress`), set in `intel_display_driver_suspend()` before `drm_atomic_helper_suspend()` (line 692), cleared in `intel_display_driver_resume()`. Gate: `d330_82h0_panel() && display->suspend_commit_in_progress` (DME helper pattern from the failed patches, vlv_dsi.c DMI match on `82H0`). Rationale for keeping it display-level: KWin's post-resume modeset and any user modeset run long after, with the flag cleared.

## 2. Precedent landscape (who skips panel power-off at suspend)

| Precedent family | What it does | Verdict for v10.0 |
|---|---|---|
| Upstream i915 (7.0 tree) | No quirk anywhere that skips DSI panel power-off at suspend; only suspend-adjacent DSI code is the GLK "cold boot(s3/s4)" prepare comment (vlv_dsi.c:779) | Nothing to copy; DMI quirk infra in vlv_dsi.c:1867-1899 is the precedent for *how* to gate |
| Chrome OS (chromeos-5.4, chromeos-5.15) | **Did not patch it** — teardown identical to mainline, no DMI quirks in the file. GLK Chromebooks of this era resumed from the same full power cycle and (per fleet behavior) worked, because their panel init was complete | Confirms no hidden platform trick in kernel code; also confirms Windows/Chrome OS re-init *works* when the init content is right |
| Windows (igdkmd64.sys) | Re-runs full DSI power-state init every S3 resume (`SB_SAVESTATE/SB_RESTORESTATE`, `SetPanelPower`, `SendPPSPacket`) and works — its init includes direct TCON programming beyond VBT | Windows succeeds where Linux fails; keep-hot sidesteps the missing Linux init entirely |
| eDP/PPS world (intel_pps.c) | `intel_pps_off()` cuts panel power at disable; PPS VDD retention via `disable_power_well` is runtime-PM only | Suspend still power-cycles eDP panels; no precedent there either |
| PSR (panel self refresh) | Keeps the *image* while the SoC runs (DC5/6, s0ix fstates); display core still DC9-gated at S3 | Not a precedent for S3; do not open PSR work |
| Android/fastboot kernels | Historically full panel power-off at display-off/suspend; always-on-display tricks rely on panel GRAM (self-refresh panels), not on holding rails | No GLK-tablet-relevant precedent found this session (search API down — LOW, gap) |
| Burn-in/power-limit risk of holding rails | LCD (not OLED) 800x1280 10" panel: logic rails only (backlight off) | Negligible burn-in risk; small battery cost — see §4 |

**What did Chrome OS do for S3 on these tablets?** In the kernel: nothing special — stock teardown (fact 6). Their S3 story on GLK relied on the panel tolerating a full power cycle + their complete init at resume. (Their *boot* story — fastboot, panel skip on handover — is a different, well-known effort and is not relevant to suspend.)

## 3. Experiment ladder (DMI-gated 82H0, one per CI iteration)

Common infra: existing CI pipeline, deploy script with sha-verified rollback, `scripts/capture_dsi_dumps.sh`, `i915_dsi_regs` dump node (survives re-probe), D330SEQ/D330GPIO/D330DLY ftrace markers, eyes-on verdicts only. Add the shared `d330_82h0_panel()` helper + the suspend flag from §1 (one-time, part of E1).

### E1 — skip the panel-side teardown at suspend (the question's experiment (a), sharpened)

**Patch site:** `intel_dsi_post_disable()`, vlv_dsi.c. Gate the three panel-facing actions behind the suspend flag:
- skip `MIPI_SEQ_DISPLAY_OFF` (901),
- skip `MIPI_SEQ_ASSERT_RESET` (926),
- skip `MIPI_SEQ_POWER_OFF` (929),
- in `intel_dsi_disable()`: skip the SHUTDOWN DCS (850-855) and **keep** `MIPI_SEQ_BACKLIGHT_OFF` (842).

Keep ALL host-side teardown (fifo drain 885-891, `clear_device_ready` 904, PLL off 917) — DC9 wipes it regardless and resume expects it. Also skip the `panel_power_off_time` update only if it would poison `wait_panel_power_cycle` later (it won't: stale timestamp → no stall; leave the line as-is to avoid new branches).

**Firmware interaction:** S3 still saves full SoC power (DC9 untouched — the display die still power-gates; only the PMIC panel rail stays on). Panel survives electrically iff (i) the SoC GPIO pad for 144 retains its high level into S3 (SoC pads are themselves inside the power-down boundary — if the pad float to low-Z at S3 entry, the PMIC may cut the rail at entry no matter what the kernel did), and (ii) the PMIC's sleep mode doesn't force the display rail off. Both unknowns are exactly what E1 measures — it is simultaneously the experiment and the rail-survival probe (the hardware logic-analyzer probe of the panel flex from the v9.0 audit's "next instrument" list can be slotted in before E1 if the user wants to de-risk first; software E1 fails fast and cheap either way).

**Success:** ftrace shows suspend ends after `BACKLIGHT_OFF` (no DISPLAY_OFF/ASSERT_RESET/POWER_OFF). At-wake post-commit dump = X=Y set + eyes-on image → **v10.0 done** (resume then only needs a display re-enable; E2 may not even be needed if KWin's commit alone relights — test as-is first). Dump = X=Z / black → rails were cut anyway; go to E3.

### E2 — warm-resume enable: skip panel re-init when the panel is known-hot

**Patch site:** `intel_dsi_pre_enable()`, vlv_dsi.c. Keep-hot flag (set at E1's skipped suspend, cleared whenever POWER_OFF runs) → skip:
- `MIPI_SEQ_POWER_ON` (772) — GPIO 144 already high; writing it again is idempotent, skipping it avoids a rail glitch,
- `MIPI_SEQ_INIT_OTP` (792) — **this is a GPIO 160 reset toggle; on a hot panel it would re-reset the TCON and throw away the kept state. Must be skipped.**

Keep: `DEASSERT_RESET` (774, no-op with 160 held high — harmless), the whole GLK link bring-up (`glk_dsi_enable_io` 777, `device_ready` 785, prepare), `MIPI_SEQ_DISPLAY_ON` (810 — DCS 0x11/0x29 is the wake/refresh signal if the TCON auto-standby'd during the S3 signal loss), backlight (815-816).

**Firmware interaction:** none new; GOP-powered rails already up from E1. The bet: re-trained link + DISPLAY_ON suffices without OTP init. If the TCON needs a full re-init anyway, this lands at X=Z like everything else — falsification is cheap.

**Success:** ftrace shows pre_enable without POWER_ON/INIT_OTP; post-commit dump = X=Y + eyes-on.

### E3 — rail/TCON survival discriminator (only if E1 falsified)

**Patch site:** instrumentation, not behavior — extend the dump node or a debugfs one-shot: after resume link bring-up but BEFORE `INIT_OTP`, send a DCS read (e.g. panel ID 0x04 / 0xDA-0xDB) over the re-trained link via `intel_dsi_host_transfer()` (vlv_dsi.c:132) and log the response (D330 marker).
**Meaning:** panel answers → TCON alive with rails held at S3 (then the missing piece is only the right wake order — go to E4); panel silent + X=Z → rails were cut (or TCON dead) → kernel-side ladder exhausted, escalate to the hardware logic-analyzer probe (v9.0 audit's next instrument; measures GPIO 144/160 rail behavior across S3 directly).

### E4 — wake-order tuning (only if E3 shows a live TCON that still doesn't light)

Variants, one per iteration: longer LP-11 hold before DISPLAY_ON (VBT 0x11→200ms→0x29 timing from block 53 as the reference); DEASSERT_RESET + 10 ms before DISPLAY_ON without INIT_OTP toggle; POWER_ON re-write + DISPLAY_ON combo. Grounded in the VBT sequence content (GOP_DSI_RE_FINDINGS §2 table).

### Dead experiments (do not spend iterations)

- **(c) "hold backlight PWM + rail registers across S3"** — impossible host-side: DC9 wipes all display MMIO (fact 3). Host register holds are disproven *by construction*, independent of the bug. The panel-rail half of (c) IS E1. Backlight must stay OFF through S3 (battery, LED lifetime, and the backlight is a separate already-disproven lever — v8.0 row, bl_power).
- **(d) "defer PPS power-down to the resume path"** — falsified twice: row 31 (power cycle at top of pre_enable → "black but lit") and the v8.0 early-cycle patch (made the modeset fail). PPS registers aren't even the panel-power path on this machine (GPIO 144 is).
- **`disable_power_well=0`** — source-disproven (fact 8).
- **s2idle as the escape** — falsified (NO_CLEAN_FIX_PROOF row 3; DC9 on GLK regardless of s2idle, source-verified).

## 4. Risks

| Risk | Severity | Notes / mitigation |
|---|---|---|
| PMIC cuts display rail at S3 entry regardless of GPIO 144 | High probability, **decisive** | Ends the whole ladder. E1 fails fast (one CI build + one rtcwake session); E3's DCS read tells you whether the TCON died with the rails. The definitive measurement is the logic analyzer on the panel flex (v9.0 next instrument) — optional but de-risks before spending E2-E4 |
| SoC GPIO pad (144/160) doesn't hold state into S3 | High probability | Same failure mode as above; same answer. Note the kernel cannot hold a pad it cannot address after DC9 — the hold must be latched in the PMIC/sleep-well hardware |
| Battery cost of hot panel rails through S3 | Low | Logic rails only (backlight off): order tens of mW on a ~1-2 W S3 budget. If E1 works, quantify with one battery-drain check |
| Panel electrical limits (burn-in, rail endurance) | Negligible | LCD, not OLED — no burn-in mechanism; rails-on-hours identical to a long desktop session |
| Rail sequencing violation at wake (t10/t11) | Low-medium | If the rail blips at S3 entry/exit while GPIO 160 is high, the TCON re-powers without a reset cycle → may come up un-initialized. VBT T11-T12 = 5000 ms; `intel_dsi_wait_panel_power_cycle()` already enforces the delay before any power-on |
| E2 skipping INIT_OTP on a panel that DID lose state | Low | Symptom = same black as today; no damage path (INIT_OTP is the init, not the damage). E2 only ships behind the keep-hot flag |
| Holding 82H0-only gate wrong on other machines | Low | Same DMI product-name gate as the three v9.0 patches; harmless outside 82H0 (proven three times) |
